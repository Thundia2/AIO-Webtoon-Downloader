## Common traps (learned the hard way)

These are mistakes prior sessions actually made. Read them before you
trust your git/PR view.

- **`git log upstream/main..HEAD` LIES about merged-ness after a squash-merge.** GitHub's "Squash and merge" produces a NEW commit SHA on upstream from the squashed subject. The original local commits keep their pre-squash SHAs, which never appear on `upstream`, so `git log upstream/main..HEAD` reports them as "ahead" even though their content is fully merged. A branch that's content-identical to upstream can still show 5-10 "ahead" commits this way. **Always verify by content**:
  ```bash
  git fetch upstream
  git diff upstream/main..HEAD --stat   # empty = content-identical, nothing actually ahead
  ```
  Live example this session: `fix/whole-codebase-review-sweep` showed **26 "ahead"** of `upstream/main`, but `git diff --stat` was EMPTY — fully merged via #58's squash (`63a6550`).
- **`gh pr list --state all --author Thundia2 --limit 20` is the source of truth** for what's open vs merged. Don't infer state from branch names on disk — branches outlive their PRs. Run this before framing PR scope — it also DECIDES the branch target: an OPEN PR means commit onto that PR's branch; none open means cut fresh off `upstream/main`.
- **Branches the user is "done with" can still exist locally and on `fork`**, with pre-squash SHAs that look unmerged. Don't try to push, PR, or rebase from them unless the user explicitly asks. If unsure, ask.
- **`args.output_dir` is mutated mid-run** in `aio-dl.py:main()` from the user-facing root (`"manga"`) to the per-series folder (`"manga/<Title>"`) at the `allocate_series_output_dir` call. The persistence layer (`run_params.json` for resume) MUST capture the pre-mutation root via `_output_dir_root_for_resume`, or resume re-nests one level deeper every cycle. Same applies to `args.epub_dir`. See the matching architectural invariant below.
- **Cut fresh branches off `upstream/main` ONLY when opening a NEW PR (none currently open)** — even if your current branch already has the working-tree edits. The current branch may carry redundant (already-squash-merged) SHAs that bloat the PR's "ahead" count without adding content. `git stash` carries the working-tree edits across the branch switch cleanly when the content is identical. **This trap INVERTS while a PR is open: do NOT cut a new branch then — commit onto the open PR's branch** (a fresh cut would strand the fix outside the PR the owner is going to merge; see "How to ship" below).

## Architectural invariants (verify after any change)

- **mangafire `fast_download_images` is INHERITED from `BaseSiteHandler`** (no override). Verify: `python -c "from sites.mangafire import MangaFireSiteHandler; h=MangaFireSiteHandler(); print(type(h).fast_download_images.__qualname__)"` → `BaseSiteHandler.fast_download_images`. If this prints `MangaFireSiteHandler.fast_download_images`, the override leaked back in — delete it.
- **mangafire's `/api/*` is SIGNED again as of 2026-08-02 — every call needs a `vrf=` query param** (`403 {"message":"Missing token."}` without one, `"Invalid token."` when it doesn't match the params sent). This RETIRES the former "NO VRF, NO browser" invariant. **Don't try to reimplement the token**: it's a stream cipher over the path + serialized query (ciphertext length == plaintext length exactly, so there is no timestamp/nonce and tokens NEVER expire), and the implementation ships as *virtualized bytecode* — custom binary deserializer, seed-derived 512-entry opcode permutation tables, VM dispatch loop, `DisableDevtool` — re-seeded per build. Instead `sites/mangafire_vrf.py` calls the site's OWN signer: it is an ordinary ES module (shipped under the DECOY name `polyfill-<hash>.js`) whose export installs an axios request interceptor, so handing that export a fake axios instance yields the interceptor and `config.params.vrf`. The chunk is discovered **behaviourally** (import every module the page loaded, probe each export) — never by filename, which is build-stamped and rotates. Verified byte-for-byte against tokens the live site emitted. **Cost is a one-time browser boot, NOT comix's per-series render**: signing is an in-page call (~15ms; a 13-spec batch incl. cold Chromium launch = 1.3s; disk-cached = free), tokens are session-independent (they replay from a cold cookieless curl_cffi session), so signing alone needs the browser **whenever Cloudflare is off** — see the Cloudflare invariant below for what changes when it is on. `EXPENSIVE_PROBE` stays False either way, and image downloads ALWAYS stay on the curl_cffi fast path (the `*.mfcdn*.xyz` CDN is a different host and is not challenged — verified 2026-08-19: a real page URL returns a 536 KB `image/jpeg` under `impersonate="chrome"`). Disk cache (`<profile>/vrf-cache.json`) is namespaced on the signer chunk URL, NOT on `window.__build`/`__config` — the site DELETES both globals once its bundle reads them, so they are `undefined` by the time a `page.evaluate` runs. Residual "same chunk, rotated key" is covered by the backstop in `_api_get`, which re-signs ONCE on a token rejection. `--mangafire-vrf-*` flags stay DELETED (signing needs no CLI surface). Offline coverage: `tests/test_mangafire_vrf.py` (47, shared with the Cloudflare invariant below). Endpoints (all JSON, all now requiring `vrf`): search `GET /api/titles?keyword=`, detail `GET /api/titles/{hid}`, chapters `GET /api/titles/{hid}/chapters?language=&sort=number&order=asc&page=N&limit=100` (limit caps at 100 → HTTP 422 above it; paginate on `meta.hasNext`), pages `GET /api/chapters/{chapterId}` → `data.pages[].url` returned **verbatim** (CDN host varies per chapter — `l1n.mfcdn2.xyz`, `o48.mfcdn3.xyz`, … — all serve 200 directly, even without a Referer, so the old rewrite is gone). URL id is the short base-36 `hid` (numeric `id` 404s); `_extract_hid` parses both new `/title/{hid}-{slug}` and old `/manga/{slug}.{hid}` — old library URLs 301-redirect AND their hid was preserved on the relaunch, so existing series update/resume with **zero re-match** (the persisted url becomes the new form). Chapter list has duplicate `official`/`unofficial` entries per number → deduped one-per-number, **prefer `official`** (override env `MANGAFIRE_CHAPTER_TYPE`; both types serve real pages). `EXPENSIVE_PROBE=False` now (was True — a page fetch is one cheap JSON GET). Offline coverage: `tests/test_komikku_metadata.py::test_mangafire_*_from_json` + `tests/test_cli_flag_parsing.py::test_mangafire_vrf_flags_removed`.
- **mangafire.to is behind a Cloudflare Managed Challenge, and the ONLY client that gets past it is a correctly-launched browser** (2026-08-19). Measured against the live site: plain `requests`, **impit** (`browser="chrome"`), **curl_cffi** (`impersonate="chrome"`) and **cloudscraper** were ALL served `Just a moment...` for both the homepage and `/api/*` — every headless tier this repo owns is blocked, so there is no TLS-impersonation fix. The reported symptom was a misdiagnosis the code produced itself: `_bootstrap` navigated, landed on the interstitial, ran its module scan against it and truthfully reported **`no vrf signer among 0 module candidates`**, blaming the signer for a network-level block. Four rules now hold. (a) **Nothing probes the DOM before `_ensure_cleared` says the page is real** — that ordering IS the fix for the misleading error. (b) **The launch presents ONE identity**: `channel="chromium"` + a pinned UA, the pair from `sites/browser_identity.py`'s measured table (NEITHER lever is sufficient alone — the pin only moves the UA header, the channel only moves `Sec-CH-UA`). This is not cosmetic: on a **cold throwaway profile the hardened headless launch auto-cleared the challenge in 3.2s**, which the old plain-`headless=True` launch — advertising `HeadlessChrome` in both the UA and the hints — never could. Verified clean on a live page: UA `Chrome/147.0.0.0`, `userAgentData.brands` `Chromium 147`, `webdriver: false`. **The channel launch is RETRIED (`_CHANNEL_LAUNCH_ATTEMPTS`=3) before downgrading**, because Chromium locks its user-data-dir and this profile is shared by every process the app spawns (searcher.js and downloader.js are separate); a collision makes Chrome self-exit with `exitCode=21`, surfacing as `TargetClosedError` — which is nothing like "unsupported channel" but hit the same except branch and permanently downgraded the run's identity (observed live 2026-08-20). `_channel_unsupported` is a deliberate WHITELIST: an unrecognised error is retried, since misreading a transient collision as an incompatibility costs the whole run its identity while the reverse costs one launch. **Those retries are now the SECOND line of defence — see (e).** (c) When it does NOT auto-clear, the handoff is gated on `interactive_solve_allowed()` **and** `cf_solver_available()`, so search / `--list-chapters` / the update-check fail cleanly instead of demanding a human; tier 1 is `crawlee_utils.get_cf_session` (zendriver clicks the Turnstile, cookies injected + its UA pinned), tier 2 is a headed relaunch of mangafire's OWN persistent profile. Prompt budget mirrors comix's, and a SUCCESS never counts against it. (d) **`_api_get` reads through the browser once challenged** (`fetch_api_json` → same-origin `fetch()` in the cleared page), sticky per process via `_api_via_browser`, with plain HTTP tried first so the fast path survives Cloudflare being switched off. **Do NOT transplant `cf_clearance` into cloudscraper** — that is the exact recovery comix already proved cannot work. Debug seams: `AIO_MANGAFIRE_FORCE_CF=1` fires the detector once, `AIO_MANGAFIRE_NO_INTERACTIVE_CF=1` fails fast instead of opening a window (use it in tests so a regression into prompting fails rather than hangs), `AIO_MANGAFIRE_CF_SOLVE_TIMEOUT` overrides the 180s wait. (e) **ONE process at a time owns the profile, and contention must never downgrade the identity** (2026-08-20 — this is what made library update checks fail on every mangafire series while ordinary downloads worked). The two launches are **different binaries with different lock behaviour**: `channel="chromium"` is full Chromium and REFUSES a held user-data-dir, while the channel-less fallback is `chromium_headless_shell` and **gets in anyway**. Since the desktop sweep runs up to 8 concurrent `--list-chapters` PROCESSES, the fallback was *guaranteed* to be taken and *guaranteed* to succeed under contention — silently swapping the clean identity for one leaking `HeadlessChrome` in **Sec-CH-UA, `userAgentData.brands` AND `fullVersionList`** (all three measured), after which Cloudflare never auto-clears and a background op may not ask a human. Fix is two-sided: `sites/profile_lock.py` is an OS-level (kernel-released, so a killed proc can't strand it) cross-process lock that `_start` takes **before any launch** — waiting `_PROFILE_WAIT_DEFAULT_S`=45s, env `AIO_MANGAFIRE_PROFILE_WAIT_S` — held across `_cleanup` so a mode switch/UA relaunch stays inside one hold and released only by `close()`; and `UI-source/electron/main.js` caps `_SERIAL_BROWSER_SITES` (`mangafire`, `comix`) at ONE in-flight check so the wait is normally never exercised. Contention is deliberately **not** a sticky `_mark_unavailable` verdict (the peer exits and the next call works). Related: `_identity_degraded` stops a fallback launch writing `aio-stable-ua.txt`, and `browser_identity.stabilize_user_agent` now also **reduces the Chrome build** (`147.0.7727.15` → `147.0.0.0`) — the two binaries otherwise report different versions, so the cache OSCILLATED and each flip cost a teardown+relaunch (that is why the channel-failure banner printed twice per series), and the unreduced form is itself a UA no real Chrome sends. Live-verified: 4 concurrent `--list-chapters` all exit 0 with real chapter counts, waits of 3.3/8.8/12.5s logged, and ZERO occurrences of "launch failed" / "falling back" / "HeadlessChrome". Offline coverage: `tests/test_mangafire_vrf.py` (56) + `tests/test_profile_lock.py` (13).

- **Every fuzzy score in this repo goes through `sites/fuzzy_match.py`, and it NORMALIZES 3 codepoints before scoring** (2026-08-12, M6 of the Android port). rapidfuzz ships TWO backends and imports whichever exists: a compiled `*_cpp` extension, or the pure-Python `*_py` reference modules. Desktop has the compiled one; **Android does not** (Chaquopy's index serves no rapidfuzz, so `android/wheels/` vendors rapidfuzz's own pure-Python wheel — same library, same version, `.py` files byte-identical to a desktop install). **The two backends are NOT bit-identical**, which matters because the gates are exact numbers (WRatio >= 75, `token_set_ratio` >= 85, `_TITLE_BAND_DELTA` = 8). An exhaustive sweep of all 1,114,112 codepoints found exactly two causes: **(a) 3 SEPARATOR codepoints** — `utils_py.default_process` filters with `re.compile(r"(?ui)\W")` and Python regex counts `_` as a WORD character, so the Python backend keeps underscores the C++ one replaces; separately the Python tokenizer is `str.split()` (Unicode whitespace) against a C++ tokenizer that splits on ASCII only, making U+0085 and **U+00A0** separators to one backend and ordinary characters to the other. **U+00A0 is the one that bites in practice — scraped HTML titles carry `&nbsp;`.** Mapping those three to a plain space makes both backends see the identical string, and 96,348 assertions over the real corpus + 20k adversarial random pairs then agree exactly. **(b) 5536 UNICODE-SKEW codepoints** (4824 of them CJK extensions, plus U+0130 whose Python `.lower()` expands to `i`+U+0307 where C++ gives plain `i`) where rapidfuzz's bundled C++ tables predate Python 3.13's Unicode database — **NOT normalized on purpose**, because a CJK ideograph is not a separator; measured worst case 4.35 points, and 1 of 130 real series contains any such codepoint. The normalizer is `str.translate`, **length-preserving and non-collapsing** — a string without those 3 characters is returned unchanged and scores exactly as it always did, which is what makes this safe on desktop; collapsing space RUNS would have changed the far more common double-space case, which both backends already agree on. Three call sites, all via the wrappers (`wratio` / `processed_wratio` / `processed_token_set_ratio`): `search_orchestrator._best_title_match` (the bare-WRatio cross-site search path — the one most likely to meet a `&nbsp;`), `external_metadata._score_candidate_detail`, `external_metadata._author_match_score`. `_load_rapidfuzz` survives as the feature-named ImportError. Offline regression: `tests/test_fuzzy_match.py` (16, incl. a full-Unicode sweep asserting the separator set is still exactly those 3 — ~5s, runs by default). Device parity: `aio_android.diagnostics()` reports `rapidfuzz_backend` + a `rapidfuzz_fingerprint` that MUST equal desktop's (verified identical across both backends).

## How to ship changes to upstream

`main` on `upstream` is protected — no direct pushes. Everything lands via a PR
whose head branch lives on `fork`. **The user merges the PR from the GitHub UI.**

**Sequencing rule — finish first, THEN commit.** Complete the fix, run the
verification suite, and confirm the result with the user BEFORE anything is
committed or pushed. The commit/push decision is made at that point — never
mid-fix, never pre-planned at the start of a session. Until then, work lives in
the working tree only.

**Branch decision — check `gh pr list --state open --author Thundia2` first:**

- **A PR is OPEN → commit onto its existing branch. Do NOT cut a new branch.**
  PR scope integrity is a non-goal in this repo; unrelated fixes and features
  stack into the same open PR to maximize what lands when the owner merges.

  ```bash
  git checkout <open-pr-branch>
  git add <files>
  git commit -m "..."              # same commit-message conventions as below
  git push fork <open-pr-branch>   # the open PR picks it up automatically — no gh command needed
  ```

- **No PR open → cut fresh off `upstream/main`** (so no already-merged pre-squash
  SHAs bloat the "ahead" count) and open a new PR:

```bash
# 1. Make changes, smoke-test (run the verification suite above).

# 2. Cut a fresh branch off upstream/main, carrying the working-tree edits.
#    git diff upstream/main..HEAD --stat is usually EMPTY (the last branch was
#    content-merged upstream), so the stash pop applies cleanly.
git fetch upstream
git stash push <changed files>
git checkout -b feat/<name> upstream/main
git stash pop

# 3. Commit (one cohesive commit unless features are cleanly separable). Cite
#    the reviewer comment in the body if addressing feedback.
git add <files>
git commit -m "concise subject

Body explaining what + why.

Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>"

# 4. Push the NEW branch to fork (NOT upstream — main is protected).
git push fork feat/<name>

# 5. Open the PR to upstream; the USER accepts/merges it from the GitHub UI.
gh pr create --repo zzyil/AIO-Webtoon-Downloader --base main \
  --head Thundia2:feat/<name> --title "<title>" --body-file <somefile>
```

Commit/push only once the fix is complete and the user has signed off — the
decision point is end-of-fix, not the start of the session. While a PR is open,
stacking commits onto its branch via `git push fork <branch>` IS the default
shipping path (not a follow-up exception); the user does the final merge. (As a
collaborator you *could* push the branch to `upstream` and open a same-repo PR
instead — but the fork route above is the default.)

## DO NOT do

- **Don't `git push --force` to a `fork` branch that has an open PR** unless the user explicitly says so. The PR's inline review comments are tied to specific line numbers; force-pushing breaks those references. (This is review-comment integrity, which still matters — distinct from PR *scope* integrity, which doesn't in this repo.)
- **Don't cut a new branch while a PR is open** — commit onto the open PR's branch and `git push fork <branch>`. Fresh branches off `upstream/main` are only for when NO PR is open; the open PR is the bus everything rides until the owner merges it.
- **Don't commit or push mid-fix, and don't decide the commit/push plan up front.** Finish the fix, run the verification suite, confirm with the user — the commit/push call happens then, not before.
- **Don't squash or amend `a871d0d`** (the merge commit). It's a true merge with two parents (upstream `0cf0813` + local `20e8bbf`); squashing destroys that and breaks `git log --graph` history.
- **Don't push to `upstream/main`** — it's a protected ref (the push is rejected anyway). PR branches live on `fork`; `upstream` is the PR base and the user merges via the GitHub UI. There is no `origin` remote anymore.
- **Don't re-litigate strategy decisions** (see table above). If the user wants to revisit one, they'll say so explicitly.
- **Don't bring back retired sites** (Bato, mangapark, bato_mirrors). Upstream retired them on purpose. The fork's old docs entries were silently re-listing them; that was the regression zzyil caught in his first review pass.
